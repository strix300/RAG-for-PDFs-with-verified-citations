Тестовое задание
Бизнес-задача
Требуется разработать backend-сервис, который принимает документ, сохраняет его содержимое в векторное хранилище и позволяет задавать вопросы по документу, возвращая ответ со ссылками на конкретные места в тексте. Разработка пользовательского интерфейса в задание не входит.
Условие по объему. Входной документ может содержать до 100 страниц, а его индексация - занимать несколько минут.

Ответы только по документу. Если в документе нет сведений, необходимых для ответа, сервис обязан сообщить об этом, а не формулировать ответ на основе общих знаний модели. Каждое утверждение в ответе должно опираться на найденные фрагменты документа.

Без истории. Каждый запрос обрабатывается независимо. История диалога не хранится и не учитывается, контекст предыдущих вопросов не используется: ответ определяется только текущим вопросом и содержимым документа.
Характер поиска. Документы содержат точные обозначения - номера пунктов, наименования сторон, суммы, даты, специальные термины. Поиск только по смыслу такие обозначения теряет, поиск только по словам не находит переформулировки того же условия. Поэтому поиск строится в три шага: плотные векторы дают семантическую близость, разреженные векторы BM25 дают точное совпадение по словам, результаты обеих ветвей объединяются в общий список кандидатов. Затем кандидаты обязательно переупорядочиваются реранкером, и в контекст языковой модели попадают только верхние фрагменты после переранжирования.
Пример результата
Ответ на вопрос по документу:
{
  "answer": "Штраф за просрочку поставки составляет 0,1% от стоимости
             товара за каждый день просрочки.",
  "found": true,
  "citations": [
    {
      "text": "За нарушение сроков поставки Поставщик уплачивает
               Покупателю неустойку в размере 0,1% ...",
      "page": 12,
      "section": "4.2 Штрафные санкции"
    }
  ]
}

Если ответа в документе нет, поле found равно false, citations - пустой список, а answer содержит сообщение об отсутствии сведений.
Состав API
Структуру маршрутов и JSON-контракты определить самостоятельно и описать в README.md. Сервис должен поддерживать следующие операции:
•	загрузка документа и запуск его индексации;
•	получение состояния фоновой задачи индексации;
•	получение списка загруженных документов;
•	получение ответа на вопрос по конкретному документу.
Для операции получения ответа предусмотреть необязательный параметр, добавляющий в ответ диагностические сведения: сколько фрагментов дала каждая ветвь поиска, сколько кандидатов осталось после переранжирования и какие из них использованы при формировании ответа.
Технические требования
•	Реализовать только backend API на FastAPI. Пользовательский интерфейс не требуется.
•	Индексация документа выполняется фоновой задачей. Для выполнения фоновых задач использовать Celery, в качестве брокера сообщений - Redis. Состояние задачи должно быть доступно через API.
•	Векторное хранилище - Qdrant. Фрагменты всех документов хранятся в одной коллекции, разделение документов выполняется фильтром по идентификатору документа, а не созданием отдельной коллекции на каждый документ.
•	Отдельная реляционная база данных не требуется: сведения о документе хранятся в payload его фрагментов, состояние фоновых задач - в Redis.
•	Payload фрагмента. Для каждого фрагмента сохранять не менее следующих полей: doc_id, doc_title, chunk_index, page_from, page_to, section, text, char_start, char_end. Для полей, по которым выполняется фильтрация, настроить payload-индексы.
•	Гибридный поиск. Для каждого фрагмента хранить в одной точке два вектора: плотный, построенный моделью эмбеддингов, и разреженный по алгоритму BM25. Поиск выполняется по обеим ветвям, их результаты объединяются средствами Qdrant в рамках одного запроса, а не двумя отдельными запросами со склейкой результатов в коде. Способ объединения и количество кандидатов каждой ветви задаются конфигурацией.
•	Переранжирование. Объединенный список кандидатов обязательно переупорядочивается отдельной моделью-реранкером; в контекст языковой модели передаются только верхние фрагменты после переранжирования. Модель реранкера, количество кандидатов на входе и количество фрагментов на выходе задаются переменными окружения.
•	Разбиение документа на фрагменты, построение эмбеддингов и взаимодействие с языковой моделью выполнять средствами LangChain.
•	Структуру ответа валидировать с помощью Pydantic.
•	Сервис не хранит состояние между запросами на получение ответа: сессии, треды и память диалога не реализуются.
•	Настройки моделей и подключений вынести в переменные окружения.
•	Предусмотреть обработку ошибок и повторные попытки при временной недоступности языковой модели и векторного хранилища.
Результат выполнения
Необходимо предоставить:
•	исходный код решения и README.md с инструкцией запуска;
•	краткое описание архитектуры, принятых решений и доработок, необходимых для использования решения в production;
•	примеры запросов к API с результатами их выполнения, включая вопрос с точным обозначением (номер пункта, сумма, наименование) и вопрос, ответа на который в документе нет.
